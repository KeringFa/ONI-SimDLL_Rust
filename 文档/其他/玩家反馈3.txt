A few extra ideas that might be worth checking:
Adaptive worker count for different CPUs
Instead of using one fixed rule for all CPUs, maybe Auto mode could choose worker count based on detected topology:
physical cores
logical processors
SMT / Hyper-Threading enabled
processor groups
maybe cache/core layout if available
A rough heuristic could be:
int workerThreads;

if (manualWorkerThreads > 0) {
    workerThreads = manualWorkerThreads;
} else if (logicalProcessors <= 4) {
    workerThreads = Math.Max(1, logicalProcessors - 1);
} else if (physicalCores <= 6) {
    workerThreads = Math.Clamp(physicalCores - 1, 2, 5);
} else if (physicalCores <= 8) {
    workerThreads = Math.Clamp(physicalCores, 4, 8);
} else {
    workerThreads = Math.Clamp(physicalCores, 6, 12);
}
The exact numbers may need testing, but the general idea is to avoid blindly using all logical threads. The game still needs CPU time for the main thread, render thread, audio, OS, and other mods.
Manual worker override as a safety valve
Even with a good Auto mode, a manual override would be very useful because CPUs and saves behave differently.
For example:
{
  "WorkerThreads": 0
}
Where:
0 = Auto
1-16 = manual worker count
This helps users test what is best on their own CPU without needing a new mod build.
Cache-friendly chunk scheduling
From the binary strings, I noticed files like:
src\c_simulation\frame_processor.rs
src\c_simulation\element_chunk.rs
src\c_simulation\conduit_temperature.rs
src\c_simulation\building_temperature.rs
src\d3_rayon\scheduler.rs
Maybe the scheduler could process simulation data in larger, stable, contiguous chunks instead of many tiny scattered jobs.
For a grid-based simulation, something like this may be more cache-friendly:
chunks.par_iter_mut().for_each(|chunk| {
    process_cells_in_chunk(chunk);
});
This should help not only X3D CPUs, but also normal Intel/AMD CPUs, because memory locality and lower scheduling overhead are generally useful.
Avoid jobs that are too small
If each Rayon job is too small, thread scheduling overhead can become visible, especially on lower-core CPUs.
Maybe Auto mode could choose chunk size based on worker count and active cell count:
let min_cells_per_job = 2048;
let job_count = (active_cells / min_cells_per_job).clamp(worker_threads, worker_threads * 4);
The goal is to keep workers busy without creating too many tiny jobs.
Reduce false sharing between workers
If multiple workers write to nearby cells or shared arrays at the same time, cache line bouncing can hurt frame pacing.
Possible improvements:
per-worker temporary buffers
merge results after the parallel phase
align hot per-thread counters/buffers to cache lines
avoid multiple threads writing to adjacent small fields in the same cache line
Example idea:
#[repr(align(64))]
struct WorkerScratch {
    // per-worker temporary data
}
Dirty-region / active-chunk processing
If the simulation processes the whole map every frame, it may waste work on stable regions.
Maybe it would help to track active chunks:
gas/liquid changed
temperature changed
building emitted/consumed element
conduit changed
neighbor chunk needs update
Then stable vacuum/solid regions can be skipped or updated less often.
This could improve performance across all CPUs, especially late-game saves.
Reduce main-thread waiting
If FPS drops happen because the main thread waits for the simulation thread, more worker threads will not always help.
Optional timing logs could show this:
frame total
worker compute time
main thread wait / frame_sync wait
merge/copy-back time
active chunk count
actual worker count
If worker compute time is low but main thread wait is high, the bottleneck may be synchronization. If worker compute time is high, then chunk scheduling or worker count may be the issue.
Avoid per-frame allocations
If any simulation stage allocates temporary Vec/HashMap/String/log objects every frame, it may cause stutter.
Reusable per-worker buffers could help:
thread_local! {
    static SCRATCH: RefCell<Vec<CellUpdate>> = RefCell::new(Vec::with_capacity(4096));
}
Or store scratch buffers in the simulation state and clear/reuse them each frame.
In short, I think the most useful general improvements may be:
correct CPU topology detection
adaptive Auto worker count
manual worker thread override
cache-friendly chunk scheduling
avoiding tiny jobs
reducing false sharing
reducing main-thread wait time
avoiding per-frame allocations
optional timing logs to identify the real bottleneck
I am not sure which part is currently the main bottleneck, but these changes may help make performance more stable across different CPUs
