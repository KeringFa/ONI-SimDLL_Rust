Hi, I did some testing on my side and found one thing that might be related to the FPS fluctuation.
My CPU is AMD Ryzen 7 7800X3D, 8 physical cores / 16 logical threads.
But in Player.log, SimDLL_Rust reports:
[SimDLL_Rust] CpuInfo: HT present, cores=1 flags=1
So I wonder if the CPU topology detection is possibly reading my CPU as only 1 physical core. When I play, FPS can sometimes stay around 60-70, but sometimes drops to around 30-40 with unstable frame pacing. I am not sure if this is the main cause, but it looks like it could affect the thread scheduling mode or Rayon worker count.
A few ideas that might be worth checking:
CPU core counting
The related part might be around CpuInfo and GetLogicalProcessorInformationEx.
Maybe the parser needs to handle SYSTEM_LOGICAL_PROCESSOR_INFORMATION_EX as variable-sized records. From what I understand, each record should advance by record.Size, rather than assuming a fixed struct size.
Something like this idea, just as a rough reference:
int physicalCores = 0;
int logicalProcessors = 0;

GetLogicalProcessorInformationEx(RelationProcessorCore, IntPtr.Zero, ref len);
IntPtr buffer = Marshal.AllocHGlobal(len);

if (GetLogicalProcessorInformationEx(RelationProcessorCore, buffer, ref len)) {
    int offset = 0;

    while (offset < len) {
        var header = Marshal.PtrToStructure<SYSTEM_LOGICAL_PROCESSOR_INFORMATION_EX_HEADER>(
            IntPtr.Add(buffer, offset)
        );

        if (header.Relationship == RelationProcessorCore) {
            physicalCores++;

            // Count all logical processors in this physical core.
            // This part may need to handle one or more GROUP_AFFINITY masks.
            foreach (var groupMask in processorCore.GroupMasks) {
                logicalProcessors += BitOperations.PopCount(groupMask.Mask);
            }
        }

        offset += header.Size;
    }
}
For a Ryzen 7 7800X3D, the expected result should probably be:
physical cores = 8
logical processors = 16
It may also be safer to treat IsProcessorFeaturePresent(PF_HTT) only as a feature flag, and derive SMT from something like:
bool hasSmt = logicalProcessors > physicalCores;
Maybe a fallback would help too:
if (physicalCores <= 1 && Environment.ProcessorCount >= 4) {
    logicalProcessors = Environment.ProcessorCount;
    physicalCores = Math.Max(1, logicalProcessors / 2);
}
This way, if topology parsing fails on some CPUs, Auto mode will not fall back into a 1-core scheduling path.
Manual worker thread option
Would it be possible to add a manual worker thread override in the config?
Maybe something like:
{
  "LogEnabled": false,
  "HyperThreadOptimizationEnabled": true,
  "WorkerThreads": 0
}
Where 0 means Auto, and users can choose values like 4 / 6 / 8 / 12 / 16.
The selection logic could be something like:
int workerThreads;

if (config.WorkerThreads > 0) {
    workerThreads = config.WorkerThreads;
} else {
    workerThreads = Math.Clamp(logicalProcessors - 2, 2, 12);
}
For my 7800X3D, I would probably test 6 or 8 first. I feel using all 16 logical threads may leave too little room for the game main thread / render thread, so a manual option could help users find the most stable setting.
Rayon thread pool setup
I noticed the binary contains strings related to Rayon, such as:
src\d3_rayon\scheduler.rs
src\d3_rayon\mod.rs
src\d3_rayon\d1_pipeline.rs
RAYON_NUM_THREADS
RAYON_RS_NUM_CPUS
d3: rayon ThreadPool build failed
GlobalPoolAlreadyInitialized
So maybe it would be useful to pass the chosen worker count into the Rust side before the Rayon pool is initialized.
A rough idea could be:
let pool = rayon::ThreadPoolBuilder::new()
    .num_threads(worker_threads)
    .thread_name(|i| format!("simdll-d3-{i}"))
    .build()?;
A local/persistent Rayon ThreadPool might also be more stable than relying on global auto-detection, especially after restart/reload. I noticed GlobalPoolAlreadyInitialized appears in the binary strings, so maybe avoiding repeated global pool initialization could help stability.
Optional timing logs
If it is not too much trouble, maybe an optional lightweight timing log could help diagnose frame drops, for example:
frame total
frame_sync wait
D1/D2/D3 worker time
heat exchange time
element update time
conduit temperature time
message handling time
actual worker count used
This would make it easier to tell whether FPS drops are caused by worker imbalance, main-thread waiting, or one simulation stage taking too long.
Again, I am not sure this is the exact cause, but the cores=1 line looks suspicious on an 8c/16t CPU, so I wanted to report it with my logs.
