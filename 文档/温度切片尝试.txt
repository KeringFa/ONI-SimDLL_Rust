温度切片（D4）尝试记录
================================================

结论先行：D4 温度切片并行方案已实测证伪，于 2026-09-05 全面下线。
本文记录完整技术路线与失败原因，供后续性能工作避坑参考。

------------------------------------------------
1. 方案动机
------------------------------------------------
游戏主物理循环中，温度阶段（格子间热传导 + 相变）是大头之一。
原版 ONI 本身把温度按「区域 × 行带」切给多线程（ParallelTaskQueue）。
本项目早期（方向1/D1）在此基础上做了超线程亲和、区域装箱（D2 rayon）、
三段式流水线（D3），D4 试图在区域**内部**再切成瓦片（32×32 基准），
让单个大区域也能铺满多核。

------------------------------------------------
2. 实现要点（已交付的技术资产）
------------------------------------------------
- d4-slice feature + d4_slice/ 模块（mod.rs / slice_grid.rs / temperature.rs）
- SliceGrid：区域 → 瓦片网格（边界收窄、halo 收缩、不跨区域）
- 切片事件缓冲 + RowMarks 逐行定序合并（保证与原版**逐位一致**的追加顺序）
- SliceEventPool：跨帧复用 grid + 每切片缓冲（消除每帧分配）
- 调度接入：update_data 里 D4 分支把温度跨全部区域统一跑，其余阶段 skip_temperature
- 并行：rayon 持久池（与 D3 共用，避免嵌套池）

正确性验证：600+ 测试含多区域逐位一致、事件顺序敏感性实证，全部通过。
也就是说 D4 在**正确性上完全成立**——它是性能上输了。

------------------------------------------------
3. 证伪过程（实测数据）
------------------------------------------------
3.1 基准测试（test 环境，160×274 满水伪随机温度场）
    串行 6.9ms/帧 vs 切片并行 101ms/帧 → speedup 0.07x（并行反而慢 15 倍）

3.2 冗余探针（probe 计数）
    切片版每格算 4 对（up/left/right/down），串行每格算 2 对（right/down）。
    实测配对计算量 = 串行的 1.99 倍（≈×2）。

3.3 用户游戏内实测（真实存档，perf 日志）
    多区域大基地（11 区域，7 线程）：切片 OFF 帧时间 8.2ms；
        ON（64×64）掉 2~6 帧；ON（8×8）掉更多（700 片调度爆炸）。
    单星：ON 与 OFF 帧数无可见差异。

3.4 温度占比实测（stage profiler）
    单星（串行）：温度 CPU 2.83ms / 帧墙钟 13.6ms = 占 20.8%。
    多星（D2 并行）：温度被 7 核摊薄，实际墙钟占比约 10~18%。
    → 温度不是帧时间瓶颈；即便理想并行也最多省 ~17%（单星），
      ×2 代价吞掉大部分收益。

------------------------------------------------
4. 根本原因：×2 配对计算是「瓦片分解」的固有税
------------------------------------------------
串行 update_temperature_pair(A,B)：compute_pair_delta 算 1 次，写 A、B 两格。
瓦片并行下 process_cell 不能写邻居格（跨切片 = 数据竞争），于是退化为：
    - A 作为第一元素算 (A,B) → 只写 A
    - B 作为第二元素（up/left 方向）**再算一次** (A,B) → 只写 B
同一个配对被算 2 遍，结果相同却无法共享（跨切片传值违背并行初衷）。

探针显示 up/left「白算率 0%」（每次计算都写入了有效半格，非浪费）——
但**计算本身重复**，这才是 ×2 的本质。计算量 ×2 + rayon 调度 + 缓冲合并
> 并行收益（温度无等待、纯计算密集，并行只摊核不省总量）。

------------------------------------------------
5. 前辈模组（simSimDLL）的做法：方向分解，不做瓦片
------------------------------------------------
前辈 SimDLLPlus 的 UpdateDataPara（C++/OpenMP）：
    - cellVector 方向列表：cellsL2R（每行一段）/ cellsB2T（每列一段）等
    - UpdateTemperature(cell, ncell) 一次算 delta **同时写两个 updatedCells**
    - 并行安全靠「方向互斥」：横向对只在 L2R/R2L，纵向对只在 B2T/T2B，
      同帧不同方向不碰同一对 → 无 ×2
    - 代价：每帧只处理 4 方向中的 2 个（tick 奇偶轮换）→ 温度收敛减半/帧，
      靠多帧累积（原版本是 Jacobi 迭代，可接受）
    - 用「每帧一半方向」换「每对只算一次」——时间片方向轮换策略

启示：前辈无 ×2，但代价是牺牲逐位一致（方向轮换会改变结果序列）。
本项目 D4 追求「与串行逐位一致」（600 测试护栏），与方向分解天然冲突。

------------------------------------------------
6. 结论与决策
------------------------------------------------
- 温度占帧时间 ~21%（单星）且已被 D2 行带覆盖收益空间 → 并行重构 ROI 低
- D4 瓦片方案 ×2 不可消除（除非改 halo 缓冲架构，需大重构且收益不明）
- 前辈方向分解无 ×2 但牺牲逐位一致，与项目测试哲学冲突
- 决策：全面下线 D4（删 d4_slice 模块 + feature + 调度分支）；
  切片尺寸下拉 UI 保留（供未来换方案复用）；C# 导出 stub 保留（防加载崩）
