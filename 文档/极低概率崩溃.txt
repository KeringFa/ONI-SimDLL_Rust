极低概率崩溃：EMBARK 后首个 sim tick 的 HandleVector<CallbackInfo> 越界
=====================================================================

状态：已闭环（根因定位 + 修复，2026-08-11 实测验证通过）。
历史：2026-08-09 样本 n=2（首次崩、后续新建大量游戏未再崩）；当时按
"复现步骤 + 日志取证"处理未盲改，最终经静态对照 + 复现路径实测闭环。

一、现象
---------------------------------------------------------------------
1. 新建游戏，选人阶段点击 EMBARK 按钮后的黑屏时刻崩溃（世界画面尚未显示，
   ALERT 音乐正常播放，初始存档未生成——初始存档在确认 ALERT 提示后）。
2. Player.log 报错堆栈：
   ArgumentOutOfRangeException: Index was out of range
     at HandleVector`1[T].IsVersionValid(Handle handle)
     at Game.IsManuallyReleasedHandle(HandleVector<CallbackInfo>.Handle)
     at Game.StepTheSim(float dt)
     at Game.UnsafeSim200ms / SimEveryTick / Update

二、崩溃机制（已对照反编译源码确认）
---------------------------------------------------------------------
1. C# Game.StepTheSim（Assembly-CSharp/Game.cs L1119-1130）遍历 simDLL 返回的
   GDU callbackInfo：handle.index = callbackInfo.callbackIdx，随后
   IsManuallyReleasedHandle → callbackManager.IsVersionValid(handle)。
2. HandleVector.IsVersionValid（Assembly-CSharp-firstpass/HandleVector.cs）：
   index = handle.index & 0xFFFFFF；return versions[index] == version。
3. callbackIdx 为 -1 时：handle.index = -1 → (-1) & 0xFFFFFF = 0xFFFFFF = 16777215
   → versions[16777215] 越界；callbackIdx 超过 C# callbackManager 注册数同样越界。
4. callbackManager 初始 256 项（Game.cs L432），由建筑 OnSpawn 注册
   （ElementEmitter/Door/GeothermalVent 等，ElementEmitter.cs L29-30）。
5. simDLL 侧 push callback_info 的 5 处：frame_processor 3 处（dig / set_cell_properties
   / cell_modifications）、element_emitter 2 处（blocked / unblocked），均过滤
   -1/0xFFFFFFFF。故非法值来源 = 未覆盖的消息路径，或 cb 索引与 C# 注册数不同步
   （顺序/数量差异），偶发出现。

三、已排除的路径（2026-08-09 排查）
---------------------------------------------------------------------
1. ModifyCellMessage 与 Rust CellModification 布局逐字段一致（28B，Pack=4，
   callbackIdx 均为第 2 个字段），消息解析无错位。
2. AddElementEmitterMessage 与 Rust AddElementEmitterMsg 布局一致（16B）。
3. DLC handler（DefineWorldOffsets / ClearUnoccupiedCells /
   ResizeAndInitializeVacuumCells / SetWorldZones）均已实现，非空桩。
4. element_emitter / frame_processor 事件在 d3 阶段 B 串行执行，无并行竞争。
5. "勾选启用日志但不重启"与崩溃无关：OK 只写 config.json，当前会话不调
   RS_SetLogLevel、不初始化 logger，新建游戏不重新调 SIM_Initialize。

四、诊断日志（已埋点，启用日志后复现可取证）
---------------------------------------------------------------------
1. src/c_simulation/element_emitter.rs：blocked/unblocked callback push 时
   tracing::info 记录 cb（u32）与 cb_signed（i32），event 标记
   element_emitter_blocked_callback / element_emitter_unblocked_callback。
2. src/a_framework/save_load.rs：PrepareGameData 填充 GDU 时记录
   callback_info count（每帧一条）。
3. 复现步骤：启用日志 → 重启 → 新建游戏（重复多次）→ 崩溃后收集
   simdll.log（重点：崩溃前最后一帧的 callback_info count 与 emitter push 的
   cb 值；若 cb 为 -1/超限即为直接来源）。

五、附带观察
---------------------------------------------------------------------
- 若后续仍无法复现，可考虑在 Rust 侧对 callback_info push 增加"疑似非法值
  过滤"（如 callback_idx < 0 或 > 0xFFFF 时丢弃并告警），但需先确认合法上限
  语义，勿凭猜测改动（严格对照原版 L134789-135039 / L141577-141610）。

六、根因与修复结论（2026-08-11）
---------------------------------------------------------------------
【根因】ELEMENT_EMITTER_MANAGER 是进程级全局静态（element_emitter.rs L247-248），
新建游戏/读档时从未清空，残留上一局的发射器记录。

1. 原版注册表是 SimData 成员：SimDLL_Source.c L121473（SimData 构造时
   ElementEmitter::ElementEmitter）与 L122565（析构时销毁）→ 每次新世界
   分配 = 全新空注册表，旧句柄天然不存在。
2. Rust 全局静态必须显式清空。save_load.rs 两条新世界分配路径
   （handle_allocate_cells L156-157 / handle_initialize_from_cells L1469-1470）
   只清了 radiation/disease emitter，漏掉 element_emitter（clear_element_emitters
   全仓库零生产调用点）。
3. 崩溃链：同一进程先玩一局大基地（门/发射器等把 C# callbackManager 撑过
   256 槽）→ 回主菜单新建游戏 → 首个 sim tick 遍历残留记录，blocked/unblocked
   翻转时把上一局的 callbackIdx（≥256 的旧槽号）推进 callback_info → C#
   HandleVector.IsVersionValid 对 versions[index] 无边界保护 → 越界崩溃。
4. 为何"极低概率 + 仅首帧 + 首次崩后大量新建不再崩"：需同时满足"上一局槽号
   已 ≥256、残留 cell 落在新局 region 内、首帧恰好翻转、cb 超出新局当前容量"；
   崩溃使进程重启 → 静态清零，后续新建自然不再触发。

【修复】（2026-08-11 落地）
1. save_load.rs 两条分配路径补齐清空（与 radiation/disease 同约定）：
   clear_element_emitters（崩溃根因）+ clear_element_chunks +
   clear_building_temperature + clear_building_to_building +
   clear_disease_consumers（同类"原版随 SimData 重建、本项目全局静态"）。
2. building_temperature.rs / building_to_building.rs 各补 count 访问器
   （供回归测试断言，模式同 element_chunk_count 等）。
3. 回归测试 allocate_cells_clears_all_global_registries：五个注册表各注入
   1 条残留记录 → handle_allocate_cells → 断言全部归零。

【验证】
1. cargo test --lib：552 通过 / 0 失败。
2. cargo build --release --features d3-rayon 成功，DLL 已同步
   Local\SimDLL_Rust\SimDLL_RS.sim；发布 DLL 无测试符号。
3. 玩家实测（2026-08-11）：按复现路径（大基地存档 → 主菜单 → 新建游戏）
   连续多次，无崩溃；电解器等发射器堵/通行为与修复前一致。

【未采用】push 点"cb 超限即丢弃"的防御过滤：可压住崩溃但会静默丢弃本应
触发的发射器回调，且掩盖根因；仅作症状层兜底，不替代清空。
