极低概率崩溃根因分析：EMBARK 后首个 sim tick 的 HandleVector<CallbackInfo> 越界
=====================================================================

分析日期：2026-08-11
分析人：Kimi-K3（WorkBuddy）
前置文档：极低概率崩溃.txt（2026-08-09 排查记录）
结论性质：静态代码审查定位的根因（未改动任何文件，未实测复现）

---------------------------------------------------------------------
一、根因结论
---------------------------------------------------------------------

跨游戏/跨存档的状态残留：Rust 侧 ElementEmitterManager 是进程级全局静态
（element_emitter.rs L247-248，Lazy<Mutex<...>>），在每次新建游戏/切换世界时
从未被清空。

save_load.rs 的 handle_allocate_cells（AllocateCells 消息处理器，每次新游戏/
读档分配新 SimData 时触发）L153-157 只清空了 radiation_emitter 和
disease_emitters 两个管理器：

    // 新世界分配 = 存档切换：上一存档的 RadiationEmitter 记录全部作废。
    // 原版注册表在 Sim 内、跨存档靠 Remove 消息清理；本项目为全局静态，
    // 显式清空避免"上个存档辐射残留"（旧发射器继续向新世界发射）。
    crate::c_simulation::radiation_emitter::clear_radiation_emitters();
    crate::c_simulation::disease_component::clear_disease_emitters();

注释表明作者已意识到"全局静态跨存档残留"这一缺陷模式，但漏掉了
clear_element_emitters()（element_emitter.rs L250）。全仓搜索确认：
clear_element_emitters 除定义外没有任何生产代码调用点（仅测试内的
reset_for_test 间接调 clear()）；SIM_Initialize -> clean_up()
（save_load.rs L27 起，只释放 SaveBuffer/gSim/gDisease/gSimData）也不清它；
而新建游戏不会重新调用 SIM_Initialize（前报告第五节已确认）。

---------------------------------------------------------------------
二、崩溃的数学条件（C# 侧，已对照反编译源码）
---------------------------------------------------------------------

1. HandleVector.IsVersionValid（Assembly-CSharp-firstpass/HandleVector.cs
   L186-191）：

       byte num = (byte)(handle.index >> 24);
       int index = handle.index & 0xFFFFFF;
       return num == versions[index];   // index >= versions.Count 即抛
                                        // ArgumentOutOfRangeException

2. callbackManager 初始容量 256（Game.cs L432），Initialize 直接填充 256 项，
   versions.Count = 256；仅当并发注册数超过 256 时 Count 才逐一增长
   （HandleVector.Add，freeHandles 为空时 versions.Add）。

3. 因此崩溃当且仅当：callbackIdx & 0xFFFFFF >= 当前 versions.Count。
   新游戏开局注册数远小于 256，Count 恒为 256，故崩溃值 = 低 24 位 >= 256
   的任何 callbackIdx（含 -1 = 0xFFFFFFFF -> 16777215）。

---------------------------------------------------------------------
三、关键排除：单个游戏会话内不可能产生越界值
---------------------------------------------------------------------

1. 全仓搜索确认 callback_info 的 push 点恰好 5 处，与前报告一致：
   - frame_processor.rs L146（dig）、L369（set_cell_properties）、
     L505（cell_modifications）：均过滤 callback_idx != -1；
   - element_emitter.rs L458（unblocked）、L475（blocked）：均过滤
     cb != 0xFFFFFFFF。
2. 这 5 处推送的值全部来自 C# 当会话发来的消息字段（DigMessage /
   CellPropertiesMessage / ModifyCellMessage / AddElementEmitterMessage），
   而消息里的句柄由当会话 callbackManager.Add 分配，其索引必然 <
   当会话 versions.Count（Count 只增不减，句柄分发时已含扩容）。
3. 结论：在单一游戏会话内，数学上不存在越界 callbackIdx 的来源。
   越界值只能来自"不属于当会话 callbackManager 的句柄"——即上一局的残留。

---------------------------------------------------------------------
四、完整崩溃链条
---------------------------------------------------------------------

1. 上一局（同进程，尤其是玩过建筑多的存档）：
   C# 侧每扇门注册 2 个回调（Door.cs L688 开 / L714 关），每个 ElementEmitter
   注册 2 个（ElementEmitter.cs L30-31），每个 GeothermalVent 注册 2 个
   （GeothermalVent.cs L269-270）。大门多的基地并发注册可超过 256，
   callbackManager 扩容后，后续注册的发射器 blocked/unblocked 句柄索引
   可以 >= 256。这些句柄值随 AddElementEmitter 消息存入 Rust 侧
   ElementEmitterData.blocked_cb_idx / unblocked_cb_idx。

2. 退出主菜单、新建游戏（同进程，不重调 SIM_Initialize）：
   Rust 的 ELEMENT_EMITTER_MANAGER 中上一局的 ElementEmitterData 记录
   原样保留——记录是纯数据（发射参数、[row,col] 坐标、blocked_state、
   elapsed_time、两个 cb 索引），不持有旧 SimData 指针，因此不受
   AllocateCells 重建 SimData 影响。C# 侧 callbackManager 则是全新的
   256 项 versions。

3. 新局首个 sim tick：
   update_element_emitters（element_emitter.rs L364 起）遍历 self.items，
   残留记录满足触发条件的概率很高：
   - rec.cell 是旧世界坐标，新世界地图尺寸相近时多半落在 region 范围内；
   - elapsed_time 是上一局退出时的剩余值，相当比例已 >= emit_interval，
     首 tick 即进入发射判定；
   - 新世界该坐标的堵/通状态与残留 blocked_state 几乎必然不同
     -> 触发 blocked/unblocked 翻转分支 -> push 上一局的 callbackIdx。

4. 该值经 GDU（save_load.rs L662-672）交给 C#，Game.StepTheSim
   （Game.cs L1120-1131）构造 handle 后调 IsManuallyReleasedHandle ->
   IsVersionValid：低 24 位 >= 256 时 versions[index] 越界
   -> ArgumentOutOfRangeException，崩溃于 EMBARK 后黑屏时刻、
   世界画面出现之前、初始存档生成之前。

---------------------------------------------------------------------
五、为什么所有观测特征都吻合
---------------------------------------------------------------------

1. "首个 sim tick"：残留记录的 elapsed_time 是上一局退出时的剩余值，
   相当部分已满足发射间隔，tick 1 立即发生堵/通翻转并推送旧句柄；
   之后新局的 AddElementEmitter 逐渐覆盖/追加记录，窗口期集中在开局。

2. "极低概率"：需同时满足——
   a) 同一进程内玩过 callbackManager 并发注册数 >256 的局
      （大基地：门 x2 + 发射器 x2 + 通风口 x2 的回调注册累积）；
   b) 有残留记录在新局首 tick 恰好触发堵/通翻转；
   c) 该记录的 cb 索引 >= 新局 versions.Count（256）。
   任一条件不满足都不崩（见第六节"幽灵回调"）。

3. "首次崩、后续新建大量游戏未再崩"：崩溃导致进程重启，静态管理器清零；
   全新进程中第一局无残留可崩；后续连续新建的都是短测试局，发射器少、
   句柄索引 <256，即便残留也不越界。

4. n=2 均为"首次"：两次崩溃前应当都在同进程内加载过既有存档/大基地。

---------------------------------------------------------------------
六、附带发现（同一缺陷模式的关联风险）
---------------------------------------------------------------------

1. 同类未清空的全局管理器（clear_* 同样只有测试调用点）：
   - element_chunks（element_chunk.rs L270）
   - building_temperature（building_temperature.rs L396）
   - building_to_building（building_to_building.rs L172）
   - disease_consumers（disease_component.rs L466）
   这些不参与本崩溃路径，但会导致新局残留旧局数据（旧建筑温度输出、
   旧碎片记录等隐性错误）。

2. 幽灵回调：残留 cb 若 <256 且版本位碰巧为 0（fresh versions 全 0），
   IsVersionValid 返回 true，不崩溃，但 callbackInfo.Add 会在新局随机
   触发一个无关回调——隐性逻辑污染，比崩溃更难察觉。这意味着该缺陷的
   实际影响面远大于 2 次崩溃样本。

3. 句柄空间跨局单调增长：新局的 AddElementEmitter 在残留管理器上继续
   append/pop free list，emitter 句柄索引跨局累积；versions 为 u8
   （wrapping_add），回绕后旧句柄可能别名到新记录，Modify/Remove
   会作用于错误对象。

4. 原版 C++ 的注册表在 Sim 实例内，跨局依赖建筑销毁时的 Remove 消息
   清理（save_load.rs 注释已注明）；而 C# SimComponent.SimUnregister
   仅在 simHandle 有效时才发 Remove（SimComponent.cs L99-106），
   未注册完成的建筑（simHandle=-2）永不发 Remove。两条清理路径都
   不可靠，因此在本项目的全局静态架构下，"新世界分配时显式清空"
   才是正确做法（radiation/disease 两处已是先例）。

---------------------------------------------------------------------
七、取证验证方案（无需改代码，用既有埋点即可实锤）
---------------------------------------------------------------------

按前报告第四节启用日志后复现，检查崩溃前最后一帧的 simdll.log：

1. element_emitter_blocked_callback / element_emitter_unblocked_callback
   事件中的 cb 值：若 cb >= 256（或明显超过当局已注册建筑回调数），
   即实锤为上一局残留句柄；
2. 对照同帧 PrepareGameData callback_info count 与 C# 侧实际注册数，
   若出现"推送的 cb 在当局从未分配过"，同样实锤。

反向佐证（若今后想主动复现）：同进程内先加载一个门很多的后期存档
（把 callbackManager 撑过 256），退回主菜单立刻新建游戏，崩溃概率
应显著高于全新进程直接新建。

---------------------------------------------------------------------
八、修复方向建议（本次未改动任何文件）
---------------------------------------------------------------------

治本：在 handle_allocate_cells（save_load.rs L156-157 处）补调
clear_element_emitters()，并评估是否一并对 element_chunks /
building_temperature / building_to_building / disease_consumers
做同样的清空（与 radiation/disease 两处先例保持一致）。

兜底（可选，非替代）：在 5 处 callback_info push 点增加非法值过滤
（callback_idx < 0 或与当会话注册上限不符时丢弃并告警），但需先确认
合法上限语义，且这只是掩盖残留症状的防御层，不能替代清空。

注意：清空时机必须与原版 Remove 消息清理路径兼容——新局的
AddElementEmitter 在已清空的管理器上从索引 0 重新分配，与 C# 侧
新 callbackManager 的句柄空间重新对齐，语义上与原版"注册表随
Sim 生命周期重置"一致。
