CPU 超线程检测方法（SimDLL_Rust 接口 mod）
============================================

一、当前采用：P/Invoke GetLogicalProcessorInformationEx（推荐，已上线）
---------------------------------------------------------------------
文件：SimDLL_Rust/CpuInfo.cs

原理：
1. 调用 kernel32.GetLogicalProcessorInformationEx(RelationProcessorCore=0)，
   枚举所有物理核（PROCESSOR_CORE 关系条目）。
2. 每个物理核的 PROCESSOR_RELATIONSHIP.Flags 第 0 位 = LTP_HYPER_THREADING_PRESENT；
   任一核该标志置位 → CPU 启用超线程。
3. 字段用**手写偏移读取**（Marshal.ReadInt32/ReadByte），不依赖 Marshal 结构布局：
   - 条目头部：Relationship@offset+0（uint）、Size@offset+4（uint，步进用）；
   - RelationProcessorCore 条目：Flags@offset+8（byte）。

踩坑记录（2026-08-09，均已解决）：
1. 旧 API GetLogicalProcessorInformation 在本机（Win11/部分环境）返回的条目
   全是 Group 关系（Relationship=3），没有 ProcessorCore 条目 → 检测恒 false。
   → 改用 Ex 版 API。
2. Ex 版第一次调用（查询所需缓冲区大小）预期返回 false
   （ERROR_INSUFFICIENT_BUFFER），len 被设置为所需字节——不能把该 false 当失败；
   第二次调用（实际填充）才检查返回值。
3. Marshal 结构（含 ByValArray）在游戏 Mono 下布局可能与 .NET Framework 有差异
   → 改为手写偏移读取，规避布局差异。
4. 验证：本机 AMD Ryzen 7 5800H 8C16T，Ex API 返回 8 核全部 flags=1（HT 存在），
   勾选项可交互。

二、备选：WMI ManagementObjectSearcher（真实但本场景不可用）
---------------------------------------------------------------------
查询：
  SELECT NumberOfCores, NumberOfLogicalProcessors FROM Win32_Processor
判断：NumberOfLogicalProcessors > NumberOfCores → 每核多线程（超线程/SMT）。

不可用原因：
1. 需要 System.Management.dll——ONI 游戏 Managed 目录**没有该程序集**，
   mod 引用会加载失败（除非自带 DLL，增加体积与部署风险）。
2. 数据来自 WMI 服务（winmgmt）读系统规格（SMBIOS/注册表），静态值；
   虚拟机中可能报告宿主规格而非当前环境实际拓扑。
3. 性能：数十毫秒 + 服务依赖，明显慢于 P/Invoke（微秒级）。

三、兼容性对比
---------------------------------------------------------------------
| 维度         | GetLogicalProcessorInformationEx（当前） | WMI Win32_Processor（备选） |
|--------------|------------------------------------------|------------------------------|
| 系统覆盖     | Windows 7 起（覆盖 ONI 全部支持范围）    | Windows XP 起（更广，无意义）|
| 数据来源     | 内核实时拓扑（含处理器组/每核 Flags）    | WMI 服务读系统规格（静态）   |
| 虚拟化/沙箱 | 实时反映当前环境实际拓扑                | 可能报告宿主规格             |
| 性能         | 微秒级，无服务依赖                       | 数十毫秒 + winmgmt 服务依赖  |
| mod 环境     | kernel32 P/Invoke，零依赖               | 需 System.Management.dll    |
| 细节能力     | 精确到每核 HT 标志                       | 只能逻辑核>物理核间接推断    |

四、结论
---------------------------------------------------------------------
保持 P/Invoke Ex 方案；WMI 仅作理论备选（若未来遇到 Ex API 均不可用的
极端环境再加 fallback，当前 YAGNI）。
