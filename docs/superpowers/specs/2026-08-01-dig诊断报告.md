# dig 功能失效 — 诊断报告与修复方案

日期：2026-08-01
状态：**已确诊，修复方案待用户批准**

## 一、结论（一句话版）

挖掘功能本身是好的。格子挖不掉，是因为 Rust 版 `copy_sim_data_to_game` 漏掉了原版的一段"后处理"——它没有把"格子从固体变成真空"这件事，翻译成 C# 端需要的 `solidInfo` 和 `solidSubstanceChangeInfo` 两种事件。C# 收不到这两种事件，就不会刷新格子的显示，也认为这个格子仍然是固体，于是让小人一直挖一个已经被挖空的格子。

## 二、证据链

1. 游戏日志：544 条 dig 消息全部 `handled=true`，消息链路正常。
2. 插桩日志（决定性）：
   - `process_dig_points: dug=1, game_cell=88311, elem_idx=80, state=3(固体), mass=1840` → **挖掘成功，格子已清空**
   - 65ms 后同一格子：`elem_idx=211, state=0(真空), mass=0` → sim 侧确实已挖空
   - 但 C# 在随后 10 秒里持续对格子 88311 重复下达挖掘指令 → **C# 不知道格子已挖掉**
3. C# 反编译源码（`Assembly-CSharp/Game.cs`）：
   - `Grid.Solid[格子]` 只被 `solidInfo` 事件更新（Game.cs:1104 `Grid.SetSolid`）
   - 格子画面刷新只被 `solidSubstanceChangeInfo` 事件触发（World.cs:99 `MarkDirty`）
   - 挖掘任务完成依赖 `callbackInfo.Release()`（World.cs:87-90，且要求 `numFramesProcessed > 0`，Game.cs:1442）
4. 原版 C 源码（SimDLL_Source.c L132315-132373）：`CopySimDataToGame` 会遍历每条 `SubstanceChangeInfo`，对比"游戏上次看到的元素"与"sim 最新元素"，**派生出** `solidInfo` / `solidSubstanceChangeInfo` / `liquidChangeInfo`。
5. Rust 版 `copy_sim_data_to_game`（sim_data_ops.rs:102-159）：只做了数据拷贝和事件 swap，**完全没有这段派生逻辑**。

## 三、根因定位

**位置**：`simDLL_RS/src/c_simulation/sim_data_ops.rs` 的 `copy_sim_data_to_game`

**缺失**（对照原版 L132194-132373）：
1. substance_change_info 排序 + 按 cellIdx 去重（原版 L132227-132290）
2. 用 mGameData（旧）与 mSimData（新）的 cells 回填每条 entry 的 oldElementIdx/newElementIdx（原版 L132321-132337）——这也解释了为什么原版 ProcessDigPoints 敢把 old/new 都填 0xFFFF 占位
3. old≠new 时派生三类事件（原版 L132338-132371）：
   - 固态性变化 → `solidInfo`（→ C# `Grid.SetSolid`，决定格子是否可挖/是否坚固）
   - 任一侧为固体 → `solidSubstanceChangeInfo`（→ C# `MarkDirty`，刷新格子画面）
   - 任一侧为液体 → `liquidChangeInfo`

**次级 bug（顺带）**：事件向量用 `swap` 搬移且源向量不清空，导致同一事件在 sim↔game 之间乒乓、被 C# 重复消费。原版的语义是"搬移后清空源"（L132195-132214）。

## 四、修复方案

### 修改文件
1. `src/c_simulation/sim_data_ops.rs` — `copy_sim_data_to_game`：
   - 参数增加 m_game_data（旧可见缓冲）的访问
   - 事件搬移由 swap 改为"swap 后清空 sim_events 源向量"（消除乒乓）
   - 实现原版后处理：排序去重 → 回填 old/new → 派生 solidInfo/solidSubstanceChangeInfo/liquidChangeInfo（IsSolid 判定复用 `elements_table::get_element_state_by_idx`）
2. `src/a_framework/sim_thread.rs` — 调用点传入 m_game_data 指针
3. `src/c_simulation/frame_processor.rs` — substance_change_info 的 old/new 恢复为原版占位 0xFFFF（由后处理回填真实值；现有 vacuum 补丁删除，减少与原版分歧）
4. 移除全部【插桩】临时日志

### 不改的部分
- dig 消息接收、帧排队、`process_dig_points` 主逻辑（已与原版一致）
- 01 半成品项目不参考不照抄（本次未借用其代码）

### 风险与说明
- 后处理遍历 substance_change_info，每帧条目很少（挖掘级别），性能影响可忽略
- m_game_data 在 sim 线程只读访问（与原版相同的良性读读并发）
- 附带收益：此修复同样打通 C2 物理将来的固体/液体变化事件通路（不只为 dig 服务）

### 验证方式
1. `cargo build --release` 通过、现有单元测试不破坏
2. 部署到游戏目录，用户跑游戏：挖掘格子 → 格子应消失、掉落矿石、小人停止重复挖掘
3. 验证无误后移除插桩并出正式版

## 五、预计改动量

约 80-120 行新增/修改，集中在 sim_data_ops.rs 一个函数及其调用点。
